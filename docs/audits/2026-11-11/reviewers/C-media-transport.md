## Assessment

Supported 48-kHz mono LPCM and complete scope payloads pass the existing byte-identity and UDP fanout tests. A fresh 128-client bounded loopback run delivered every emitted audio and scope packet through one upstream association. A separate eight-client run combined uncached controls, background telemetry, PCM and scope without observed media loss or control timeouts. These results establish synthetic transport delivery within those short workloads; they do not establish playback quality, waterfall rendering, real-network jitter tolerance, physical RF behavior or Pi capacity.

Two pre-existing recovery/resource issues merit action: upstream outstanding sends have no application byte limit, and a media-only outage spanning more than half the 16-bit sequence space can continue suppressing recovered media for several minutes while healthy pings prevent reconnection. Neither was introduced by the latest restoration change.

## Confirmed defects and resource gaps

### C-001 — upstream pending UDP submissions have no application byte cap

- **Severity / confidence:** Medium, high confidence in the missing application bound. Real OS backlog growth and maximum achievable memory use are unverified.
- **Feature:** Upstream TX transport backpressure/resource control.
- **Locations:** `src/icom-lan/stream.js:100`–`102`; `src/icom-lan/stream.js:105`–`114`; `src/icom-lan/session.js:231`–`232`; `src/broker.js:625`–`632`. Compare downstream cap at `src/server.js:33`–`40`.
- **Trigger:** An authorized PTT/VOX owner supplies PCM faster than upstream sends complete, or upstream send completion stalls. Raw native PCM goes directly through `session.sendAudio()` into `IcomStream.raw()`. It does not use the `LanPlayback.write()` voice/finite queue caps.
- **Expected:** Explicit application bounds on retained/replayed and outstanding-send data. Overload should be observable and should discard/cancel media safely without preventing lease release.
- **Actual / proof:** `raw()` calls `socket.send()` for every submission without pending bytes, a send-queue limit or an overload return. In the offline fixture, a fake socket accepts but withholds completion callbacks. All 10,000 packets are submitted, representing **13,880,000 modeled outstanding bytes**, while the replay map correctly remains at 256 packets. This number is the sum of submitted packet lengths in the model, **not measured process RSS or an observed OS queue size**. The probe deliberately retains only lengths, not thousands of payload buffers.
- **Impact:** The upstream side lacks the downstream side's explicit overload boundary. A stalled sender or an excessive authorized media source can create unbounded application submissions and event-loop/transport pressure. Do not infer an immediate production OOM from this fixture. Replay invalidation also cannot retract data already submitted to the socket; actual stale queued delivery across a lease was not measured in this probe.
- **Provenance:** Pre-existing. `git blame` attributes these stream lines and the direct broker forwarding path to initial tracked commit `babc6dc`; latest commit does not introduce the path.
- **Smallest practical fix:** Track outstanding upstream-send bytes and completions, enforce a configurable cap, expose drops/overload, and keep TX teardown able to proceed. Limit the media path rather than blindly dropping essential control cleanup. A small application-owned generation-tagged send queue permits cancellation before submission; it cannot recall an already-submitted datagram.
- **Regression:** Delayed/error send completions, repeated floods above the cap, lease end while sends are pending, and recovery/negative counter checks. Assert caps and continued stop/release progress rather than only `replay.size`.

### C-002 — long audio-only loss causes additional silence after the network recovers

- **Severity / confidence:** Medium, high confidence in deterministic sequence behavior; narrow trigger, fixture-only recovery timing.
- **Feature:** Media recovery while heartbeat/control connectivity remains healthy.
- **Locations:** `src/icom-lan/protocol.js:44`–`45`; `src/icom-lan/stream.js:136`, `src/icom-lan/stream.js:177`–`185`, `src/icom-lan/stream.js:223`–`249`.
- **Trigger:** After sequence 1 is delivered, drop more than 32,767 audio sequence positions while allowing stream pings/heartbeats to arrive. At the nominal 100 audio packets/s used by this repository, this requires more than roughly 5 min 28 s of selective media loss. Resume at sequence 40,000.
- **Expected:** An association that receives healthy pings but cannot make media progress should eventually recover or safely establish a fresh association after the media path returns.
- **Actual / proof:** The usual 16-bit half-range comparison classifies sequences 40,000 through 40,999 as duplicates of sequence 1. All 1,000 recovered payloads are discarded; `reorder` remains empty and no gap repair/failure is requested. Pings update `lastRx`, so the existing timeout does not recover the association. The offline probe confirms delivered-after-recovery = 0, duplicates = 1,000, failures = 0.
- **Impact:** Recovered RX audio can remain absent while the association appears alive. This is **not necessarily permanent**: with continuous sequence advance, normal acceptance resumes after wrap reaches sequence 2. From resumed sequence 40,000, that is about another 25,538 packet positions, approximately 4 min 15 s at 100 packets/s. Actual rates vary. The same ordered transport class is also used by CI-V peers, but no physical CI-V outage was reproduced here.
- **Provenance:** Pre-existing initial tracked `babc6dc` sequence handling, not the latest change.
- **Smallest practical fix:** Track successful payload progress separately from last valid packet/ping. When sustained incoming IDLE data is repeatedly out of the usable sequence window and payload progress remains stalled, fail/re-establish the association with fresh IDs. Do **not** blindly reset `lastDelivered` to an arbitrary received packet, particularly on downstream TX/control streams: that can weaken replay retirement. A time-aware reorder reset needs a documented replay-safety argument; fresh association is safer.
- **Regression:** Simulate more than half a sequence space of lost audio with healthy pings, then restore media. Assert bounded safe reconnection/recovery, no stale association acceptance, and unchanged ordinary wrap/reorder tests. Add control-only and genuinely idle audio cases to avoid reconnect loops on silence.

## Coverage gaps and improvements

- Existing transport tests are meaningful about literal layouts, ordering, replay and normal wrap. The fixture's radio packet builders are independent of production encoders, but downstream integration clients use the same `IcomSession`/`IcomStream` implementation as the product. Symmetric client/server assumptions can escape these tests; literal vectors and alternative real clients remain useful.
- `tests/integration.test.js:99` sets only the synthetic radio's upstream audio sequence to 65,534. Its title says wrap across upstream and downstream associations, but it does not force the newly created downstream server peer's outer `txSeq` through wrap. Low-impact test-strengthening opportunity: set both sides' outer and inner sequence counters near wrap, and assert both independently.
- The existing server bound test constrains outbound CI-V callbacks for one client. The new C probe adds a second healthy peer, but still mocks UDP completions. NIC congestion and a genuinely slow/unreachable receiver are not equivalent to delayed callbacks; UDP does not provide end-to-end receiver backpressure. More loopback success does not prove remote playback continuity.
- No direct coverage pins `LanCapture` priming/overflow/underflow, long event-loop pause bounds, `LanPlayback` partial frames, queue limits, `drain()` cancellation or clock recovery. These helpers are exposed on sessions, but the splitter's native media path bypasses their queues. Test them as helpers without presenting their behavior as broker fanout pacing.
- New burst-loss tests should cover unrepairable loss, multiple independent gaps, variable packet sizes, reconnect while replay is requested, saturation during stop/release, and interleaved scope/control loss. Existing tests cover individual repairs well but do not establish a jitter/latency envelope.
- Benchmark packet equality is stronger than throughput alone. Capacity still needs longer duration, a defined CPU/network budget, per-client arrival-gap percentiles and drops/reorder statistics, especially on the target Pi. There is no evidence in this lane that polling starves media under the moderate workload; stronger claims would need sustained and saturated tests.

## Cross-review after independent first pass

The coordinator requested these checks only after this lane's independent assessment was complete. No other reviewer's report was used to form C-001/C-002.

- **A release/read interleave:** Reran `A-release-read-interleave.js` successfully. Source agrees: `Broker.receive()` resolves an internal cleanup promise and then calls `pump()` synchronously (`src/broker.js:566`, `src/broker.js:609`), before the asynchronous `release()` continuation can enqueue the next cleanup step (`src/broker.js:670`). A queued unrelated client read becomes pending between PTT-off and remaining cleanup; its timeout can prevent VOX-disable from being sent. This is a confirmed cleanup-ordering defect, not a media measurement. A single atomic cleanup lane/barrier should cover the full safety sequence, not only priority of each individual command.
- **E headless failed release:** Reran `E-headless-failed-release.js` on POSIX/macOS. The synthetic radio rejects stop, remains transmitting in fixture state, and the headless CLI exits 0 without an explicit unconfirmed-RX warning. `Broker.close()` awaits but discards `release()`'s false result (`src/broker.js:759`); `Splitter.close()` has no outcome propagation (`src/splitter.js:69`); the CLI prints only state and drops status messages (`src/cli.js:119`). This confirms failure reporting/exit-status weakness. It does not prove the physical radio remains keyed after its own connection/timeout behavior.
- **F previously unseen delayed PCM:** Reran `F-delayed-audio-lease.js`; the intended safety invariant fails, and old PCM reaches the synthetic radio in a second, already authorized lease on the same downstream association. The first audio packet was withheld before the server ever observed it, so `retireInbound()` has no sequence watermark that can identify it as belonging to the previous lease. This is a confirmed, **already documented native-protocol/design limitation** (`docs/architecture.md:111`–`116`), distinct from a regression in observed replay invalidation. It does not independently key TX. A guaranteed separation needs a new media association/session identity at lease boundaries and testing of client reconnect/compatibility costs. A quarantine or age bound can mitigate an assumed maximum delay, but cannot prove the age of an arbitrary unseen native UDP packet. Keep the finding distinct from C-001's unmeasured pending-socket case.

## Proposed order for this lane

1. Prioritize the independently confirmed release-order and failed-release reporting findings with their owning lanes; safety cleanup needs an uninterruptible dispatch boundary and an explicit externally visible outcome.
2. Add an upstream media outstanding-byte limit and overload accounting, with generation-aware pending work and release-progress regressions (C-001; moderate implementation/compatibility risk if cleanup shares the cap).
3. Add media-progress stall recovery using fresh association IDs, protecting replay retirement (C-002; moderate transport behavior change, narrow real trigger).
4. Decide explicitly whether the documented unseen-old-datagram limitation is acceptable. Strict lease isolation requires a compatibility-sensitive association change; age/quarantine mitigations must remain described as bounded assumptions.
5. Add direct audio helper tests and strengthen sequence-direction/sustained-load coverage. Keep physical playback/waterfall/RF and Pi capacity marked unverified until measured safely.
